# Level5 (l5) Rules

## Philosophy

l5 is infrastructure that other agents run inside. Reliability and observability are non-negotiable. Every failure mode must be handled, every state transition must be logged.

**Priorities:**
1. Reliability (if l5 breaks, all pipelines break)
2. Observability (the human must always know what is happening)
3. Project-agnosticism (no Weave-specific logic)
4. Simplicity (minimize moving parts)

## Project-Agnostic Design

l5 must work for any project, not just Weave. All project-specific knowledge comes from configuration.

**Never hardcode:**
- Domain names (backend, compute, electron)
- Directory paths specific to Weave
- Agent prompt content
- Container image names
- Build commands

**Always configure:**
- Domains and their properties (source paths, container images, rules files)
- Agent configs to mount per domain
- Timeout values
- API endpoints the container can reach

```go
// BAD - Weave-specific
func assembleWorkspace(domain string) {
    if domain == "backend" {
        copyDir("backend/", workspace)
    }
}

// GOOD - Config-driven
func assembleWorkspace(cfg DomainConfig) {
    copyDir(cfg.SourcePath, workspace)
}
```

## Podman

### Use the CLI, not a library

Shell out to `podman` via `os/exec`. A Go Podman library adds a large dependency for something the CLI handles well. Wrap the CLI calls in a thin interface for testing.

```go
// Define an interface for container operations
type ContainerRunner interface {
    Create(ctx context.Context, image string, opts CreateOpts) (string, error)
    Start(ctx context.Context, id string) error
    Wait(ctx context.Context, id string) (int, error)
    Remove(ctx context.Context, id string) error
    Logs(ctx context.Context, id string) (io.Reader, error)
}
```

### Rootless only

Never require root. All Podman operations must work rootless.

### Always clean up

Containers must be removed on completion, failure, and timeout. Use `defer` or equivalent cleanup patterns. Orphaned containers are a resource leak.

### Timeouts

Every container run must have a timeout. The orchestrator kills containers that exceed it. Never allow unbounded execution.

## HTMX

### Server-rendered HTML

l5 uses server-rendered HTML with HTMX for interactivity. No SPA, no JavaScript framework, no client-side routing.

### Minimal JavaScript

JavaScript is acceptable only for things HTMX cannot do (e.g., SSE event handling if HTMX SSE extension is insufficient). If you are writing more than a few lines of JavaScript, reconsider the approach.

### Templates

Use Go's `html/template` package. Templates are the view layer.

## SQLite

### Use `database/sql` with a driver

Standard Go database interface. Do not use an ORM.

### WAL mode

Enable WAL mode for concurrent read access:
```go
db.Exec("PRAGMA journal_mode=WAL")
```

### Foreign keys

Always enable:
```go
db.Exec("PRAGMA foreign_keys=ON")
```

### Migrations

Use numbered SQL migration files. Apply in order at startup. Never modify a migration that has been applied -- add a new one.

## SSE (Server-Sent Events)

Use SSE for streaming live updates (journal entries, status changes) to the UI. SSE is simpler than WebSockets for one-way server-to-client streams.

### Connection management

Handle client disconnects gracefully. Use `context.Done()` from the request context to detect disconnection.

## Workspace Assembly

The core contract: copy domain source code into an isolated directory, initialize a git repo, place agent configuration and rules, place the spec. The agent gets a self-contained workspace where source code is freely modifiable but orchestrator-provided files are protected.

**Key principles:**
- Copy, never mount read-write for orchestrator inputs. The container gets a disposable copy of source code (read-write), but agent config, rules, spec, and starting patch are read-only.
- `git init` + initial commit in every workspace. The agent needs a working git repo.
- Agent config is placed at `.claude/CLAUDE.md` with read-only permissions (0444) so the agent cannot modify its own instructions.
- Rules files under `.claude/rules/` are read-only (0444).
- The l5 staging volume (`/opt/l5/`) containing the spec and starting patch is mounted read-only.
- Only relevant rules files are included (e.g., backend domain gets `go.md`, not `c.md`).

## Container API Contract

Containers communicate with the orchestrator through HTTP endpoints. The orchestrator provides these endpoints; the container calls them.

**Three artifact types:**
- **Journal entries** - Progress updates, reasoning, decisions (streaming)
- **Patch** - The final `git diff` output (terminal artifact)
- **Blocked report** - A question the agent cannot resolve (terminal artifact)

A container produces exactly one terminal artifact (patch or blocked), plus zero or more journal entries along the way.

## Error Handling

### Container failures are expected

Containers can crash, timeout, or produce bad output. The orchestrator must handle all of these without crashing itself.

```go
// Every container outcome must be handled
switch run.Status {
case StatusComplete:
    // Store patch, notify UI
case StatusBlocked:
    // Store question, notify UI, await human input
case StatusTimeout:
    // Log, clean up, notify UI
case StatusError:
    // Log error, clean up, notify UI
}
```

### Log everything

State transitions, container lifecycle events, API calls, errors. The journal is the primary debugging tool.

## Testing

### Mock the container runner

Tests should not require Podman. Mock the `ContainerRunner` interface for unit tests. Integration tests that actually run containers should be tagged.

```go
//go:build integration

func TestRealContainerRun(t *testing.T) {
    // Requires Podman installed
}
```

### Test workspace assembly with real files

Workspace assembly is filesystem-heavy. Use `t.TempDir()` for test workspaces. Verify the assembled workspace has the expected structure.

## Temporary Files

**Always use `./tmp/` (project-local), never `/tmp/`.**

This matches the project-wide convention. Create the directory if it does not exist.
